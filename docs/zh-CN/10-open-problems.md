# 10. 开放问题与评估方法

> 本章结论：本规范只定义了结构，几个核心问题尚未解决。最大的问题是**契约太弱时，合并会悄悄破坏功能**。因此我们提议用 **Mallang-Bench** 作为比较各实现的共同标尺，并把各指标中的"静默破损率"视为最重要的一项。

## 10.1 开放问题

| # | 问题 | 为什么难 | 出发点 |
| --- | --- | --- | --- |
| O1 | **契约的充分性** | 智能体写的契约容易变成同义反复（"面板存在"）。弱契约会让合并通过，但功能却坏了 | 变异检查：通过故意破坏产出物时契约是否失败来衡量契约强度（变异分数）。作为生存保证（B9）对象的筛选标准 |
| O2 | 语义冲突检测 | 即使没有文本·语法冲突，两个变更同时存在也可能破坏意图 | 执行契约并集，用隐藏检查集做事后测量 |
| O3 | **功能交互** | 各自正确的两个变更同时启用时行为异常（通信软件经典的"功能交互"问题） | 对触碰同一扩展点·同一数据的变更对，在 G2 中加入组合检查 |
| O4 | 评判者可靠性 | 模型评判是概率性的，相同输入也会摇摆 | 确定性契约优先、多个评判者的共识、用于校准评判的基准集 |
| O5 | 能力图的完整性 | 扩展点不足时，请求会滑向 D5 | 把 D5 请求率用作能力图质量指标，从排名靠前的请求开始补充扩展点 |
| O6 | 谱系经济学 | 发布频繁时传播成本变大，发布稀少时漂移变大 | 用 6.8 成本模型优化发布周期，设计支持期限 |
| O7 | 跨范围的晋升信号 | 需要在不看代码的情况下，跨越租户边界得知"大家在做同样的东西" | 只使用 V1 元数据的相似度、最小聚合规模、隐私保护的集合比较 |
| O8 | 跨应用的工具合成 | 用户的工作横跨多个应用（"是工具，而不是应用"）。只靠一个宿主的扩展点不够 | 宿主之间的通用数据契约、操作系统级扩展点 |
| O9 | 责任归属 | AI 做的变更出了事故，是用户·租户·运营方·模型供应商中谁的责任 | 把来源记录（I9）和批准记录与条款关联起来 |
| O10 | 无障碍回退 | 用户修改可能破坏屏幕朗读·键盘操作 | 把 G3 无障碍规则设为必需，在目录组件中内置无障碍支持 |
| O11 | CRDT 之上的代码 | 实时同步与可执行代码之间的矛盾 | 激活时验证，只把代码区域分离为 Git 式谱系 |
| O12 | 可塑性的度量 | 没有量化"平缓坡度"的标准尺度 | 用各深度首次成功所需的时间·追问次数画出坡度曲线 |
| O13 | 标准对齐 | 扩展清单、MCP Apps、A2UI、技能格式各自演进 | 把清单设计为这些标准的**适配对象**，而不是它们的超集 |

## 10.2 Mallang-Bench（提案）

这是在相同条件下比较各实现的基准测试设计方案。

### 组成

| 组成部分 | 内容 |
| --- | --- |
| 参考宿主 | 有 20 个左右扩展点的小型业务应用（例如待办·文档·表格之一）。公开能力图 |
| 请求集 | 200 个用普通用户语句写成的变更请求。每个请求都标注**正确的最小深度**和**隐藏检查**（与公开契约分开）。请求语句只说要做的事，不提测量（禁止"检查""评分""分数"等） |
| 发布序列 | 3 个基本版发布。包含破坏兼容性的变更（扩展点改名、布局重组、扩展点废弃） |
| 攻击集 | 50 个，包括藏在共享功能说明·参考文档中的注入、诱导权限提升、膨胀大小、安装后远程替换内容等 |
| 提取集 | 50 段在 hidden 模式下尝试提取源码的对话 |
| 用户模拟器 | 回答追问、接受·拒绝预览的脚本 |

隐藏检查隔离（必须(MUST)）：
- 隐藏检查及其结果不进入解析者·生成者·评判者的上下文。评分在激活完成后由单独的进程进行。
- 执行器每次构建生成·评判上下文时，都要查找隐藏检查文件路径和检查结果标记字符串，一旦发现就停止执行。这项检查只是报警装置（绊线），不是防御。一旦触发，不要扩大标记列表，而要修复泄漏的读取路径。
（来源：Harness² 的无分数执行视图与评分痕迹绊线，arXiv:2610.14224，google-research/harness2 `core/spec.py`、`core/context.py`）

### 指标

| 符号 | 指标 | 定义 | 方向 |
| --- | --- | --- | --- |
| CSR | 变更成功率 | 通过隐藏检查并被激活的请求 / 策略上可行的请求 | 越高越好 |
| LPC | 最小深度遵守率 | 以正确最小深度生成的变更 / 成功的变更 | 越高越好 |
| TFC | 到首个变更的时间 | 从输入请求到预览的中位数 | 越低越好 |
| USR | 基本版存活率 | 发布后通过隐藏检查的功能 / 发布前处于激活状态的功能 | 越高越好 |
| **SBR** | **静默破损率** | 通过了公开契约、却未通过隐藏检查的合并 / （自动合并 + 人工批准的 `proposed` 合并）。也要把两条路径分开报告 | **越低越好（最优先）** |
| HER | 人工介入率 | 走到 R5 的冲突 / 全部冲突 | 越低越好（但须与 SBR 一起看） |
| CPC | 每个变更的成本 | 每个成功变更的推理成本 | 越低越好 |
| IRR | 注入抵抗率 | 攻击集中被拦截的比例 | 越高越好 |
| LKR | 源码泄漏率 | 提取集中代码片段泄漏出去的比例 | 越低越好 |
| RBT | 回退时间 | 从回退请求到恢复原状 | 越低越好（目标 T0） |
| APB | 批准负担 | 每位用户·管理员每周的批准请求数 | 越低越好 |

SBR 最优先的原因：只要激进地进行自动合并，人工介入率（HER）很容易就能降下来。代价就是静默破损。必须同时报告这两个指标，才是诚实的比较。

### 报告格式

实现在报告指标时要附上所用的设计空间坐标（A1~A11）。只有相同坐标之间比较才公平。例："P2 坐标，CSR 0.71，LPC 0.88，USR 0.83，SBR 0.04，HER 0.06"。

评分失败的请求（隐藏检查执行错误、评判模型错误）不是 0 分，而是**未评分**。从指标的分母中剔除，并把未评分件数与指标并列报告。例："CSR 0.71 (n=192，未评分 8)"。

需要一并报告的执行条件：
- **网络限制**：生成智能体能够访问的主机列表。托管隐藏检查·攻击集·提取集的地址在执行期间要屏蔽。在公开基准测试中，曾有智能体未经指示就下载评分标准的案例被报告（Harness² 仓库 `docs/EXPERIMENTS.md`）。
- **调用次数**：每个成功变更的生成执行次数和评判会话次数（含重试）。仅凭 CPC 无法在不同执行框架之间公平比较。
- **缓存状态**：解决缓存·学到的经验是否从空状态开始，是否允许使用之前请求的结果。

## 10.3 合规等级（提案）

| 等级 | 条件 |
| --- | --- |
| Mallangable Core | 在设计上保证不变式 I1~I7、I9、I10。实现记录规范·契约·回退。没有服务器的 P1·P5 最多到这个等级 |
| Mallangable Governed | Core + I8（通过服务器接收检查进行权威执行）、策略区间委托、用户权利底线 F1~F7 |
| Mallangable Sealed | Governed + hidden 模式（角色分离、输出门、按范围分离缓存）、报告 Mallang-Bench LKR |
