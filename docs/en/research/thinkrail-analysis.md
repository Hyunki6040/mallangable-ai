# Research note — ThinkRail (JetBrains/thinkrail)

> Conclusion of this note: ThinkRail is an **agent IDE host** that wraps the `pi` coding agent. Its target differs from Mallangable, which modifies the user's app, but the problem is the same: "a host that lets people safely accept changes an agent made". Five things are worth taking as they are. ① **Revert based on what was seen** (CAS). ② **Do not trust judge output** (malformed means failure; host fields are filled by the host). ③ **Approval is bound to the target's fingerprint and has a defined scope.** ④ **Accepted trust covers only the content at that moment** (items that appear later are checked again). ⑤ **Stored data holds no translated text, and a lexicon pack is only data that shares cannot change.** Conversely, the principle "the host does not assemble prompts" is not adopted, because Mallangable's harness is the enforcing side.

## 1. What ThinkRail is

A host that runs the `pi` agent in-process and puts an editor, diff, terminal and review UI on top of it ([`goal-and-requirements.md` L10-16](https://github.com/JetBrains/thinkrail/blob/c10f8808cee693e4abffeeb1844a132ed0a91cc5/goal-and-requirements.md#L10-L16)). It is split into three rings: the engine host, a versioned communication contract (wire), and the UI client ([`architecture.md` L19-28](https://github.com/JetBrains/thinkrail/blob/c10f8808cee693e4abffeeb1844a132ed0a91cc5/architecture.md#L19-L28)). Workspaces are git worktrees, so several agents work in parallel without colliding ([`architecture.md` L107-122](https://github.com/JetBrains/thinkrail/blob/c10f8808cee693e4abffeeb1844a132ed0a91cc5/architecture.md#L107-L122)).

Principles that overlap with or diverge from Mallangable:

| ThinkRail principle | Relation to Mallangable |
| --- | --- |
| **Trust is explicit**: what a cloned repository can put into the agent (skills, extensions, MCP servers) is loaded only after a per-project trust approval. MCP servers defined by the repository need a separate per-item approval, and the approval is lost when the item changes ([L62-65](https://github.com/JetBrains/thinkrail/blob/c10f8808cee693e4abffeeb1844a132ed0a91cc5/goal-and-requirements.md#L62-L65)) | Same direction. Corresponds to received shared features (6.9) and I4 |
| **Influence only by supply, not injection**: the host does not assemble prompts ([L57-58](https://github.com/JetBrains/thinkrail/blob/c10f8808cee693e4abffeeb1844a132ed0a91cc5/goal-and-requirements.md#L57-L58)) | Diverges. The Mallangable harness (5.6) enforces policy and selects context per role (5.10) |
| **Show, do not recompute**: the host shows the values the engine reported as they are ([L59](https://github.com/JetBrains/thinkrail/blob/c10f8808cee693e4abffeeb1844a132ed0a91cc5/goal-and-requirements.md#L59)) | Same direction. The cost display (8.10) uses `ModelPort` metering values |

## 4. What was not included

- **Schema changes**: putting E-6's "approval = target fingerprint" into a schema field was deferred. The current rule is expressed with the existing `permissions_delta`·`approved_by`. It will be added when the format for storing approval records separately from change records is decided.
- **Worktree-based workspaces as is**: Mallangable's isolation unit is the repository and its work unit is the branch (6.4). How to make working copies (worktree, temporary clone) is left as an implementation choice.
- **Exact version-pinning rule (architecture decision 10)**: this is a repository operating rule, not spec content. Only the intent, "the spec does not restate versions but records what was checked", was reflected in E-5.
- **Receipt ring cap (20 entries, 64 MiB)**: not applicable, because Mallangable revert is a pointer move.
