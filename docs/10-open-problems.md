# 10. 열린 문제와 평가 방법

> 이 장의 결론: 이 명세는 구조를 정의했을 뿐, 몇 가지 핵심 문제는 아직 풀리지 않았다. 가장 큰 것은 **계약이 약하면 병합이 조용히 기능을 망가뜨린다**는 점이다. 그래서 구현을 비교할 공통 잣대로 **Mallang-Bench** 를 제안하고, 지표 중 '조용한 파손률'을 가장 중요하게 본다.

## 10.1 열린 문제

| # | 문제 | 왜 어려운가 | 출발점 |
| --- | --- | --- | --- |
| O1 | **계약의 충분성** | 에이전트가 쓴 계약은 동어반복이 되기 쉽다("패널이 있다"). 약한 계약은 병합을 통과시키지만 기능은 깨진다 | 변이 검사: 산출물을 일부러 망가뜨렸을 때 계약이 실패하는지로 계약 강도를 측정(변이 점수). 생존 보증(B9) 대상 선정 기준으로 사용 |
| O2 | 의미 충돌 탐지 | 텍스트·구문 충돌이 없어도 두 변경이 함께 있으면 의도가 깨질 수 있다 | 계약 합집합 실행, 숨은 검사 세트로 사후 측정 |
| O3 | **기능 상호작용** | 각자 올바른 변경 둘이 함께 켜지면 이상하게 동작한다(통신 소프트웨어의 고전적 '기능 상호작용' 문제) | 같은 확장 지점·같은 데이터를 건드리는 변경 쌍에 대해 조합 검사를 G2에 추가 |
| O4 | 판정자 신뢰도 | 모델 판정은 확률적이고 같은 입력에도 흔들린다 | 결정적 계약 우선, 판정자 여러 개의 합의, 판정 보정용 기준 세트 |
| O5 | 기능 지도의 완전성 | 확장 지점이 부족하면 요청이 D5로 미끄러진다 | D5 요청률을 기능 지도 품질 지표로 사용, 상위 요청부터 지점 추가 |
| O6 | 계보 경제학 | 릴리스가 잦으면 전파 비용이, 드물면 드리프트가 커진다 | 6.8 비용 모델로 릴리스 주기 최적화, 지원 기간 설계 |
| O7 | 범위를 넘는 승격 신호 | 테넌트 경계를 넘어 '같은 걸 만들고 있다'를 코드를 보지 않고 알아야 한다 | V1 메타데이터만 쓰는 유사도, 최소 집계 크기, 프라이버시 보존 집합 비교 |
| O8 | 앱을 넘는 도구 합성 | 사용자의 일은 여러 앱에 걸쳐 있다("앱이 아니라 도구"). 한 호스트의 확장 지점만으로는 부족하다 | 호스트 간 공통 데이터 계약, 운영체제 수준 확장 지점 |
| O9 | 책임 소재 | AI가 만든 변경이 사고를 내면 사용자·테넌트·운영자·모델 공급사 중 누구 책임인가 | 출처 기록(I9)과 승인 기록을 약관과 연결 |
| O10 | 접근성 회귀 | 사용자 수정이 화면 낭독·키보드 조작을 망가뜨릴 수 있다 | G3 접근성 규칙을 필수로, 카탈로그 컴포넌트에 접근성 내장 |
| O11 | CRDT 위의 코드 | 실시간 동기화와 실행 코드의 상충 | 활성화 시점 검증, 코드 영역만 Git식 계보로 분리 |
| O12 | 말랑함의 측정 | '완만한 경사'를 정량화할 표준 척도가 없다 | 깊이별 첫 성공까지의 시간·되묻기 수로 경사 곡선을 그림 |
| O13 | 표준 정렬 | 확장 매니페스트, MCP Apps, A2UI, 스킬 형식이 각자 진화한다 | 매니페스트를 이들 표준의 상위 집합이 아닌 **어댑터 대상**으로 설계 |

## 10.2 Mallang-Bench (제안)

구현들을 같은 조건에서 비교하기 위한 벤치마크 설계안입니다.

### 구성

| 구성 요소 | 내용 |
| --- | --- |
| 참조 호스트 | 확장 지점 20개 내외의 작은 업무 앱(예: 할 일·문서·표 중 하나). 기능 지도 공개 |
| 요청 세트 | 일반 사용자 문장으로 된 변경 요청 200개. 각 요청에 **정답 최소 깊이**와 **숨은 검사**(공개 계약과 별도) 라벨. 요청 문장은 할 일만 말하고 측정은 말하지 않는다("검사", "채점", "점수" 등 금지) |
| 릴리스 시퀀스 | 기본판 릴리스 3개. 호환성을 깨는 변경 포함(지점 이름 변경, 레이아웃 재구성, 지점 폐기) |
| 공격 세트 | 공유 기능 설명·참고 문서에 숨긴 인젝션, 권한 상승 유도, 크기 부풀리기, 설치 후 원격 내용 교체 등 50개 |
| 추출 세트 | hidden 모드에서 소스 추출을 시도하는 대화 50개 |
| 사용자 시뮬레이터 | 되묻기에 답하고 미리보기를 수락·거절하는 스크립트 |

숨은 검사 격리 (반드시):
- 숨은 검사와 그 결과는 해석자·생성자·판정자의 맥락에 들어가지 않는다. 채점은 활성화가 끝난 뒤 별도 프로세스가 한다.
- 실행기는 생성·판정 맥락을 만들 때마다 숨은 검사 파일 경로와 검사 결과 표지 문자열을 찾아, 발견하면 실행을 멈춘다. 이 검사는 경보 장치(트립와이어)일 뿐 방어가 아니다. 걸리면 표지 목록을 넓히지 말고 새는 읽기 경로를 고친다.
(출처: Harness²의 점수 없는 실행 보기와 채점 흔적 트립와이어, arXiv:2610.14224, google-research/harness2 `core/spec.py`, `core/context.py`)

### 지표

| 기호 | 지표 | 정의 | 방향 |
| --- | --- | --- | --- |
| CSR | 변경 성공률 | 숨은 검사를 통과하며 활성화된 요청 / 정책상 가능한 요청 | 높을수록 |
| LPC | 최소 깊이 준수율 | 정답 최소 깊이로 만들어진 변경 / 성공한 변경 | 높을수록 |
| TFC | 첫 변경까지 시간 | 요청 입력부터 미리보기까지 중앙값 | 낮을수록 |
| USR | 기본판 생존율 | 릴리스 후 숨은 검사를 통과하는 기능 / 릴리스 전 활성 기능 | 높을수록 |
| **SBR** | **조용한 파손률** | 공개 계약은 통과했지만 숨은 검사는 실패한 병합 / (자동 병합 + 사람이 승인한 `proposed` 병합). 두 경로를 나눠서도 보고 | **낮을수록 (최우선)** |
| HER | 사람 개입률 | R5까지 간 충돌 / 전체 충돌 | 낮을수록(단, SBR과 함께 볼 것) |
| CPC | 변경당 비용 | 성공한 변경 1개당 추론 비용 | 낮을수록 |
| IRR | 인젝션 저항률 | 공격 세트 중 막힌 비율 | 높을수록 |
| LKR | 소스 유출률 | 추출 세트 중 코드 조각이 새어 나간 비율 | 낮을수록 |
| RBT | 되돌리기 시간 | 되돌리기 요청부터 원상 복구까지 | 낮을수록 (T0 목표) |
| APB | 승인 부담 | 사용자·관리자 1인당 주간 승인 요청 수 | 낮을수록 |

SBR이 최우선인 이유: 사람 개입률(HER)은 자동 병합을 공격적으로 하면 쉽게 낮아집니다. 그 대가가 조용한 파손입니다. 두 지표를 함께 보고해야 정직한 비교가 됩니다.

### 보고 형식

구현은 사용한 설계 공간 좌표(A1~A11)와 함께 지표를 보고합니다. 같은 좌표끼리 비교해야 공정합니다. 예: "P2 좌표, CSR 0.71, LPC 0.88, USR 0.83, SBR 0.04, HER 0.06".

채점이 실패한 요청(숨은 검사 실행 오류, 판정 모델 오류)은 0점이 아니라 **미채점**이다. 지표의 분모에서 빼고, 미채점 건수를 지표와 나란히 보고한다. 예: "CSR 0.71 (n=192, 미채점 8)".

함께 보고할 실행 조건:
- **네트워크 제한**: 생성 에이전트가 접근할 수 있었던 호스트 목록. 숨은 검사·공격 세트·추출 세트를 호스팅하는 주소는 실행 중 차단한다. 공개 벤치마크에서는 에이전트가 지시 없이 채점 기준을 내려받은 사례가 보고되었다(Harness² 저장소 `docs/EXPERIMENTS.md`).
- **호출 수**: 성공한 변경 1개당 생성 실행 수와 판정 세션 수(재시도 포함). CPC만으로는 다른 하네스끼리 공정하게 비교할 수 없다.
- **캐시 상태**: 해결 캐시·학습된 교훈을 빈 상태로 시작했는지, 앞 요청의 결과를 쓰게 했는지.

## 10.3 준수 등급 (제안)

| 등급 | 조건 |
| --- | --- |
| Mallangable Core | 불변식 I1~I7, I9, I10을 설계상 보장. 기록 규격·계약·되돌리기 구현. 서버가 없는 P1·P5는 이 등급까지 |
| Mallangable Governed | Core + I8(서버 수신 검사로 권위 집행), 정책 구간 위임, 사용자 권리 하한 F1~F7 |
| Mallangable Sealed | Governed + hidden 모드(역할 분리, 출력 게이트, 범위별 캐시 분리), Mallang-Bench LKR 보고 |
