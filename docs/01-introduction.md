# 1. 서론 — 왜 '말랑한 소프트웨어 아키텍처'가 따로 필요한가

> 이 장의 결론: AI가 코드를 싸게 만들게 됐지만, **기존 앱 안에 그 코드를 넣고, 안전하게 돌리고, 업데이트를 견디게 하는 구조**는 아직 표준이 없다. Mallangable-AI는 그 구조를 정의한다.

## 1.1 문제: 코드는 싸졌는데 소프트웨어는 여전히 딱딱하다

대량 생산된 소프트웨어는 평균 사용자를 위해 만들어집니다. 평균에서 멀어질수록 사용자는 자기 일하는 방식을 소프트웨어에 맞춥니다. Ink & Switch는 이 상태를 "가게에서 사 온 가전제품"에 비유하고, 사용자가 도구를 고쳐 쓰는 생태계를 **말랑한 소프트웨어(malleable software)** 라고 불렀습니다([Ink & Switch, 2025](https://www.inkandswitch.com/essay/malleable-software/)).

2025~2026년에 코드 생성 비용은 급격히 떨어졌습니다. 그러나 같은 에세이가 지적하듯 **AI 코드 생성만으로는 소프트웨어가 말랑해지지 않습니다.** 앱 생성기는 새로운 앱을 만들 뿐, 이미 쓰고 있는 앱을 고치지 못하기 때문입니다. 실무에서 막히는 지점은 세 가지입니다.

| 결핍 | 증상 | 이 문서가 다루는 곳 |
| --- | --- | --- |
| **넣을 자리 없음** (표면 결핍) | AI가 기능을 만들어도 기존 앱에 끼울 구멍이 없다. 결국 코어 소스를 직접 패치한다 | 2장 확장 지점·깊이, 5장 런타임 |
| **업데이트를 못 견딤** (지속성 결핍) | 제공사가 새 버전을 내면 사용자 수정이 깨진다. 사용자 수천 명 × 버전마다 반복 | 6장 계보·계약 보존 병합 |
| **통제할 수 없음** (거버넌스 결핍) | 누가 무엇을 바꿨는지, 그 코드가 무엇에 접근하는지, 비용은 누가 내는지 모른다 | 4장 통제 스펙트럼, 7장 신뢰, 9장 비즈니스 |

세 번째 결핍은 이론이 아니라 이미 일어난 사고입니다. 2026년 초 한 에이전트 스킬 마켓에서는 감사 대상 스킬 2,857개 중 341개가 악성으로 확인됐고([The Hacker News, 2026.02](https://thehackernews.com/2026/02/researchers-find-341-malicious-clawhub.html)), 스캐너를 도입한 뒤에도 파일 크기를 부풀려 검사를 피한 스킬이 남아 있었습니다([Unit 42, 2026.06](https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/)). 핵심 원인은 "스킬이 에이전트의 권한을 그대로 갖고 실행된다"는 구조였습니다.

## 1.2 정의

> **Mallangable 소프트웨어**란, 사용자가 자연어·화면 지목·시연으로 의도를 표현하면 AI 에이전트가 **호스트 앱이 미리 정의한 확장 지점 안에서** 변경을 만들고, 그 변경이 **계약으로 검증되고, 되돌릴 수 있게 기록되고, 상위 기준판의 업데이트를 통과해 살아남도록 관리되는** 소프트웨어다.

이름의 유래: 한국어 **말랑(mallang)** + 영어 **-able**. 영어 *malleable*(가단성, 두드려 펼 수 있는)과 소리가 같도록 지었습니다.

### 비슷한 것들과의 차이

| 방식 | 무엇을 바꾸나 | 누가 바꾸나 | 기존 앱 수정 | 업데이트 생존 | 위험 통제 |
| --- | --- | --- | --- | --- | --- |
| 설정(Settings) | 제공사가 미리 노출한 값 | 사용자 | 예(좁게) | 높음 | 높음 |
| 플러그인 | 제공사 API로 열린 부분 | 개발자 | 예 | 중간(API 변경 시 깨짐) | 생태계마다 다름 |
| 노코드 빌더 | 빌더 안의 새 앱 | 사용자 | 아니오 | 플랫폼 의존 | 플랫폼 의존 |
| 앱 생성기(바이브 코딩) | 새 앱 전체 | 사용자 + AI | 아니오 | 해당 없음 | 낮음~중간 |
| 생성형 UI(일회성) | 이번 대화의 화면 | AI | 아니오(휘발) | 해당 없음 | 카탈로그로 제한 |
| **Mallangable** | 확장 지점 안의 기능·화면·동작 | 사용자 + AI (+ 조직) | **예** | **설계 목표** | **정책으로 조절** |

## 1.3 이 문서의 기여

1. **형식 모델**: 호스트·레이어·변경·계약·정책을 정의하고, 아키텍처가 지켜야 할 불변식 10개를 제시합니다 (2장).
2. **변경 깊이 계층 D1~D5**: "가장 약한 표현으로 해결하라"는 최소 권한 원칙(Rule of Least Power)을 사용자 변경에 적용한 위험 등급입니다 (2장).
3. **설계 공간**: 11개 축의 원시 조합 **1,944,000개**를 논리·규범·권장 제약으로 걸러 **36,772개(1.89%)**, 구조 패밀리 **863개**로 정리하고, 이를 다시 계산할 수 있는 도구를 함께 공개합니다 (3장, `tools/design_space.py`).
4. **통제 스펙트럼**: 사용자에게 허용할 범위와 운영자가 통제할 범위를 '구간 위임' 모델로 정의하고, **어떤 정책도 빼앗을 수 없는 사용자 권리 하한선**을 둡니다 (4장).
5. **참조 아키텍처**: 6개 평면, 포트·어댑터 인터페이스, 벤더 중립 하네스 이벤트 모델, 검증 게이트를 정의합니다 (5장).
6. **계약 보존 병합과 계보 전파**: 사용자 수정이 기준판 업데이트를 견디는 조건과 비용 모델을 제시합니다 (6장).
7. **경험 설계 규약**: 입력 표면, 시간 등급(T0~T4), 생성 과정 표현, 용어팩, 모델 연결 흐름을 정의합니다 (8장).
8. **비즈니스 결합 행렬**: 20개 BM이 어떤 아키텍처 선택을 요구하는지 계산 가능한 형태로 연결합니다 (9장).

## 1.4 범위와 비범위

**다루는 것**
- 기존 소프트웨어(웹 SaaS, 데스크톱, 모바일, 사내 업무 도구)를 말랑하게 만드는 데 필요한 개념, 경계, 인터페이스, 선택지.
- 개인 사용자부터 기업·공공 환경까지의 통제·가시성·과금 구조.

**다루지 않는 것**
- 특정 언어·프레임워크의 구현. 이 문서는 인터페이스와 규약까지만 정의합니다.
- 특정 모델의 프롬프트 기법. 모델은 교체 가능한 부품으로 취급합니다.
- 법률 자문. 개인정보·노동·저작권 관련 내용은 설계상 고려사항으로만 적고, 실제 적용은 관할 법률 검토가 필요합니다.

## 1.5 관련 연구와 차별점

| 계보 | 핵심 아이디어 | 가져온 것 | 다른 점 |
| --- | --- | --- | --- |
| Malleable software ([Ink & Switch](https://www.inkandswitch.com/essay/malleable-software/)) | 사용자→창작자로 가는 완만한 경사, 도구 중심 | 깊이 계층의 동기, 커뮤니티 창작 | AI 에이전트·기업 거버넌스·과금까지 아키텍처로 정의 |
| 계산 매체·동적 문서 (Boxer, 1986 · [Webstrates](https://webstrates.net/), 2015 · [Potluck](https://www.inkandswitch.com/potluck/), 2022 · [Embark](https://www.inkandswitch.com/embark/), 2023) | 문서와 앱의 경계를 없애고 사용자가 계산을 겹쳐 얹음 | 원본을 건드리지 않는 겹침 레이어(2.3), 앱을 넘는 도구(O8) | 기존 상용 앱 위에서, 제공사 업데이트를 견디는 구조로 정의 |
| 완만한 경사 (MacLean et al., 1990, 위 에세이에서 인용) | 맞춤 능력이 커질 때 필요한 학습이 조금씩만 늘어야 함 | D1~D5를 '절벽 없는 경사'로 설계 | 경사의 각 단계에 위험·검증 강도를 대응 |
| [Rule of Least Power](https://www.w3.org/2001/tag/doc/leastPower.html) (W3C TAG) | 표현력이 약한 언어일수록 분석·재사용·보안이 쉽다 | "필요한 최소 깊이로 만들어라" 규칙 | 사람 대신 에이전트가 깊이를 선택하도록 강제 |
| 동적 소프트웨어 제품군(DSPL)·기능 모델 ([Capilla et al., 2014](https://research.chalmers.se/publication/198081)) | 실행 중 기능 구성, 기능 간 제약 | 설계 공간을 제약 있는 구성 모델로 계산 | 구성 주체가 제공사가 아니라 사용자+AI |
| Local-first·CRDT·Patchwork ([Ink & Switch](https://www.inkandswitch.com/project/patchwork/)) | 사용자 소유 데이터, 범용 버전 관리 | 토폴로지 선택지, 브랜치=실험 · AI 편집을 브랜치에 두고 사람이 골라 병합(Patchwork 실험 노트) | 계보(기준판 계층)와 계약 보존 병합 추가 |
| 생성형 UI 표준 ([A2UI](https://a2ui.org/), [MCP Apps](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp)) | 코드 대신 선언형 UI, 샌드박스 iframe UI | D3 산출물 형식 | 일회성이 아니라 영속·버전 관리되는 변경 |
| 에이전트 스킬·플러그인 ([Agent Skills](https://agentskills.io/specification)) | 절차를 폴더로 패키징, 여러 에이전트에서 이식 | 하네스 배포 형식 | 스킬은 절차일 뿐, 권한 강제는 아키텍처가 맡는다 |
| 프롬프트 인젝션 방어 ([CaMeL](https://arxiv.org/abs/2503.18813), [설계 패턴](https://arxiv.org/abs/2506.08837), [치명적 3요소](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) | 제어 흐름과 신뢰 불가 데이터 분리, 권한 분리 | 에이전트 역할 분리, 정보 흐름 라벨 | 코드 생성·병합 맥락에 적용 |
| 앱 내 생성 ([n.codes](https://github.com/yungookim/n.codes), [Glaze](https://www.implicator.ai/raycast-launches-glaze-a-platform-for-building-desktop-apps-through-ai-prompts/)) | 앱 기능 지도로 사용자별 UI 생성, 앱 공유·포크 | 기능 지도(capability map), 공유 흐름 | 업데이트 생존·계보·통제 스펙트럼을 일반 모델로 정의 |

## 1.6 표기 규약

- **반드시(MUST)**: 지키지 않으면 Mallangable-AI 준수 구현이 아닙니다.
- **해야 함(SHOULD)**: 타당한 이유가 있으면 벗어날 수 있지만, 그 이유를 문서화해야 합니다.
- **할 수 있음(MAY)**: 선택 사항입니다.
- 축은 `A1`~`A11`, 제약은 `L`(논리)·`N`(규범)·`S`(경고), 불변식은 `I1`~`I10`, 프로파일은 `P1`~`P7`, BM은 `B1`~`B20`으로 표기합니다.
- 숫자 중 출처 링크가 없는 값(예: 크기 상한, 점수 가중치)은 **설계 제안값**이며 실험으로 조정해야 합니다.
