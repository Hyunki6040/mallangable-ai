# 10. 未解決問題と評価方法

> この章の結論: 本仕様は構造を定義したにすぎず、いくつかの核心的な問題はまだ解けていない。最大のものは、**契約が弱いとマージが黙って機能を壊す**という点である。そこで実装を比較する共通の物差しとして **Mallang-Bench** を提案し、指標のうち「サイレント破損率」を最も重視する。

## 10.1 未解決問題

| # | 問題 | なぜ難しいか | 出発点 |
| --- | --- | --- | --- |
| O1 | **契約の十分性** | エージェントが書いた契約は同語反復になりやすい(「パネルがある」)。弱い契約はマージを通すが、機能は壊れる | 変異テスト: 成果物をわざと壊したときに契約が失敗するかどうかで契約の強度を測る(変異スコア)。生存保証(B9)の対象を選ぶ基準として使う |
| O2 | 意味的衝突の検出 | テキスト・構文上の衝突がなくても、2つの変更が共存すると意図が壊れることがある | 契約の和集合の実行、隠しテストセットによる事後測定 |
| O3 | **機能間の相互作用** | それぞれ正しい2つの変更が同時に有効になると、おかしな動作をする(通信ソフトウェアにおける古典的な「フィーチャーインタラクション」問題) | 同じ拡張ポイント・同じデータに触れる変更のペアについて、組み合わせテストを G2 に追加 |
| O4 | 判定者の信頼性 | モデルによる判定は確率的で、同じ入力でも揺れる | 決定的な契約を優先、複数の判定者による合意、判定較正用の基準セット |
| O5 | ケイパビリティマップの完全性 | 拡張ポイントが足りないと、リクエストが D5 へ滑り落ちる | D5 リクエスト率をケイパビリティマップの品質指標として使い、上位のリクエストからポイントを追加 |
| O6 | 系譜の経済学 | リリースが頻繁なら伝播のコストが、まれならドリフトが大きくなる | 6.8 のコストモデルでリリース周期を最適化、サポート期間の設計 |
| O7 | 範囲を越える昇格シグナル | テナント境界を越えて「同じものを作っている」ことを、コードを見ずに知る必要がある | V1 メタデータのみを使う類似度、最小集計サイズ、プライバシー保存型の集合比較 |
| O8 | アプリを越える道具の合成 | ユーザーの仕事は複数のアプリにまたがる(「アプリではなく道具」)。1つのホストの拡張ポイントだけでは足りない | ホスト間の共通データ契約、OS レベルの拡張ポイント |
| O9 | 責任の所在 | AIが作った変更が事故を起こしたら、ユーザー・テナント・運営者・モデル提供元のうち誰の責任か | 出所の記録(I9)と承認の記録を利用規約と結び付ける |
| O10 | アクセシビリティの退行 | ユーザーの修正がスクリーンリーダー・キーボード操作を壊すことがある | G3 のアクセシビリティルールを必須に、カタログのコンポーネントにアクセシビリティを組み込む |
| O11 | CRDT 上のコード | リアルタイム同期と実行コードの相反 | 有効化時点での検証、コード領域だけを Git 式の系譜に分離 |
| O12 | マリアブルさの測定 | 「緩やかな傾斜」を定量化する標準的な尺度がない | 深さごとの初回成功までの時間・聞き返し回数で傾斜の曲線を描く |
| O13 | 標準との整合 | 拡張マニフェスト、MCP Apps、A2UI、スキル形式がそれぞれ別々に進化している | マニフェストを、これらの標準の上位集合ではなく**アダプターの対象**として設計 |

## 10.2 Mallang-Bench (提案)

実装どうしを同じ条件で比較するためのベンチマークの設計案です。

### 構成

| 構成要素 | 内容 |
| --- | --- |
| 参照ホスト | 拡張ポイント20個前後の小さな業務アプリ(例: ToDo・ドキュメント・表のいずれか)。ケイパビリティマップを公開 |
| リクエストセット | 一般ユーザーの文で書かれた変更リクエスト200個。各リクエストに**正解の最小深さ**と**隠しテスト**(公開契約とは別)のラベル。リクエスト文はやるべきことだけを述べ、測定については述べない(「テスト」「採点」「スコア」などは禁止) |
| リリースシーケンス | 基本版のリリース3つ。互換性を壊す変更を含む(ポイント名の変更、レイアウトの再構成、ポイントの廃止) |
| 攻撃セット | 共有された機能の説明・参考資料に隠したインジェクション、権限昇格の誘導、サイズの水増し、インストール後のリモート内容の差し替えなど50個 |
| 抽出セット | hidden モードでソースの抽出を試みる会話50個 |
| ユーザーシミュレーター | 聞き返しに答え、プレビューを受け入れ・拒否するスクリプト |

隠しテストの隔離 (必須):
- 隠しテストとその結果は、解釈者・生成者・判定者のコンテキストに入らない。採点は有効化が終わった後に別のプロセスが行う。
- 実行器は、生成・判定のコンテキストを作るたびに隠しテストのファイルパスとテスト結果の目印文字列を探し、見つけたら実行を止める。このチェックは警報装置(トリップワイヤー)にすぎず、防御ではない。引っかかったら目印のリストを広げるのではなく、漏れている読み取り経路を直す。
(出典: Harness² のスコアなし実行ビューと採点痕跡のトリップワイヤー、arXiv:2610.14224、google-research/harness2 `core/spec.py`、`core/context.py`)

### 指標

| 記号 | 指標 | 定義 | 方向 |
| --- | --- | --- | --- |
| CSR | 変更成功率 | 隠しテストを通過して有効化されたリクエスト / ポリシー上可能なリクエスト | 高いほど良い |
| LPC | 最小深さ遵守率 | 正解の最小深さで作られた変更 / 成功した変更 | 高いほど良い |
| TFC | 最初の変更までの時間 | リクエスト入力からプレビューまでの中央値 | 低いほど良い |
| USR | 基本版の生存率 | リリース後に隠しテストを通過する機能 / リリース前に有効だった機能 | 高いほど良い |
| **SBR** | **サイレント破損率** | 公開契約は通過したが隠しテストには失敗したマージ / (自動マージ + 人が承認した `proposed` マージ)。2つの経路を分けても報告する | **低いほど良い (最優先)** |
| HER | 人の介入率 | R5 まで行った衝突 / 全衝突 | 低いほど良い(ただし SBR と一緒に見ること) |
| CPC | 変更あたりのコスト | 成功した変更1つあたりの推論コスト | 低いほど良い |
| IRR | インジェクション耐性率 | 攻撃セットのうち防がれた割合 | 高いほど良い |
| LKR | ソース流出率 | 抽出セットのうちコード片が漏れた割合 | 低いほど良い |
| RBT | 取り消し時間 | 取り消しのリクエストから原状復帰まで | 低いほど良い (T0 が目標) |
| APB | 承認負担 | ユーザー・管理者1人あたりの週間承認リクエスト数 | 低いほど良い |

SBR が最優先である理由: 人の介入率(HER)は、自動マージを積極的に行えば簡単に下がります。その代償がサイレントな破損です。2つの指標を一緒に報告してはじめて、誠実な比較になります。

### 報告形式

実装は、使用した設計空間の座標(A1~A11)と一緒に指標を報告します。同じ座標どうしで比較してこそ公正です。例: 「P2 座標、CSR 0.71、LPC 0.88、USR 0.83、SBR 0.04、HER 0.06」。

採点が失敗したリクエスト(隠しテストの実行エラー、判定モデルのエラー)は0点ではなく**未採点**である。指標の分母から除き、未採点の件数を指標と並べて報告する。例: 「CSR 0.71 (n=192、未採点 8)」。

一緒に報告する実行条件:
- **ネットワーク制限**: 生成エージェントがアクセスできたホストの一覧。隠しテスト・攻撃セット・抽出セットをホストしているアドレスは実行中に遮断する。公開ベンチマークでは、エージェントが指示なしに採点基準をダウンロードした事例が報告されている(Harness² リポジトリ `docs/EXPERIMENTS.md`)。
- **呼び出し回数**: 成功した変更1つあたりの生成実行回数と判定セッション数(再試行を含む)。CPC だけでは、異なるハーネスどうしを公正に比較できない。
- **キャッシュの状態**: 解決キャッシュ・学習済みの教訓を空の状態から始めたか、前のリクエストの結果を使わせたか。

## 10.3 準拠レベル (提案)

| レベル | 条件 |
| --- | --- |
| Mallangable Core | 不変条件 I1~I7、I9、I10 を設計上保証。記録仕様・契約・取り消しを実装。サーバーのない P1・P5 はこのレベルまで |
| Mallangable Governed | Core + I8(サーバーの受信検査による権威ある執行)、ポリシーの区間委任、ユーザー権利の下限 F1~F7 |
| Mallangable Sealed | Governed + hidden モード(役割分離、出力ゲート、範囲ごとのキャッシュ分離)、Mallang-Bench LKR の報告 |
