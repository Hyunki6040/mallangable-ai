レビュー対象: `README.md`, `docs/01~10`, `docs/glossary.md`, `docs/references.md`, `schemas/*.json`, `examples/*.yaml`, `tools/design_space.py`。

## 0. 要約

数値計算、スキーマの通過可否、プロファイル表、BM 行列は**機械的にはすべて正しいです。** 問題は、その数値とスキーマが仕様本文の*主張すること*を保証できない点にあります。最も大きな欠陥は5つです。

1. `A5=own` なのに、対話型の生成者(generator)に上位レイヤー(layer)の成果物を渡しています。そのため I6 と 3.2 の中核原理に正面から反します。P2 と P6 がこれに該当します。
2. **契約(contract, κ)を実行できる表現がありません。** 契約はモデルの中心なのに、スキーマには自由テキストしかなく、契約を書くのも生成者自身です。そのため I2、I7、I10、G2、B9、SBR がすべて根拠を失います。
3. **準拠の定義と推奨プロファイルが矛盾します。** Core レベルは I1~I10(I8 を含む)を「設計上」保証することを求めます。ところが P1 と P5 は、4.8 が自ら認めるとおりサーバーがないため I8 を保証できません。
4. 2.6 の深さ(depth)の定義(D3=宣言型、D4=サンドボックスコード)をそのまま適用すると、ヘッドライン数値(70,516)と、プロファイル7つのうち5つの「推奨」判定が崩れます。
5. 伝播(propagation)アルゴリズム(6.5)と契約保存マージ(contract-preserving merge, 6.7)は、そのままでは実装できません。中間レイヤーを無視し、承認待ちの親の下にある子のジョブが止まり、契約の単調性と「上位の方式に移す」が互いに食い違います。

## 3. 判断(機械で検証していない意見)

- **貢献の重み**: 設計空間(design space)の数値は、*ルールと値の解像度をこう選んだときの*算術です。この数値が実証結果のように読める文(「ほとんどの組み合わせは意味をなさない」、「最もよくある矛盾」、「構造とビジネスはおおむね分離している」)は、プログラム委員会では却下理由になります。数値は、ルール体系の内部整合性を示すデモとしてだけ主張するほうが安全です。
- **最大の未解決リスクは O1 ではなく C-02 です。** 10章は契約の十分性を「品質」の問題として扱います。しかし生成者が契約を書く限り、これは*セキュリティ*の問題です。インジェクションを受けた生成者は、自分を通過させる契約を書きます。
- **I8 と「マリアブルさ」の緊張**: ユーザー端末側での強制を案内レベルに下げる誠実さはよいことです。ただし P1 と P5 を代表プロファイルとして掲げながら Core 準拠も約束すると、読者は誤解します。レベルを分けるほう(C-03 の修正)が誠実です。
- **スキーマの範囲**: スキーマは「形」だけを検査し、仕様の中核的な保証(I4, I5, I7, I10)には文書をまたぐ検査が必要です。ところが、この検査を誰がどこで行うのか(受信検査、準拠検査ツール)がありません。v0.2 より前に `tools/` に小さな準拠検査器(conformance validator)が1つあるだけでも、「設計上の保証」は反証可能な主張になります。
- **B20(スポンサーのデフォルト値)** は、エージェントの推薦の中立性を構造的に損ないます。表示義務だけでは、モデルのコンテキストに入ったスポンサー情報が推薦を傾けるのを防げません。入れるなら「スポンサー情報はエージェントのコンテキストに入れず、UI にのみ表示」のほうが安全です。
- **D3 中心の解釈(03:262)** は、H-01 が解決されるまでは維持できません。D3 に sandboxed と native が混在しているため、「宣言型の画面までしか開かなくても」という解釈とデータが合いません。
- **よくできている点**(公平のために): 数値の再現性、スキーマと例示の通過、プロファイル・BM 行列のコードベースでの生成、壊れたリンク 0 個、出典24個中23個にアクセス可能、「出典のない数値は提案値」という表記、7.8 の保証レベル表、4.8 のクライアント PDP の限界の告知。v0.1 の草案としては珍しく検証可能な構造です。
